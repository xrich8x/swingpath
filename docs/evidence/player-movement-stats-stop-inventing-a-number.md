# Player movement stats stop inventing a number (distance_run_m)

> **CORRECTION 2026-08-28.** The far-player coverage figures quoted below for
> `yt_match40` (**11.0%**) are withdrawn as *far-player* numbers: that clip's committed
> calibration is wrong, so the pipeline labelled the NEAR player FAR
> ([yt-match40-calibration-is-wrong.md](yt-match40-calibration-is-wrong.md)). The
> conclusion of this file is UNAFFECTED — the point is that a sparse track must not be
> integrated into a confident distance, and a track that is sparse *and* the wrong person
> is a stronger case for the gate, not a weaker one.

> Evidence for the `player-movement-stats-stop-inventing-a-number` row in [docs/STATE.md](../STATE.md) (What has worked).
> Text preserved verbatim from SCOREBOARD.md at the 2026-08-26 split.

**THE DASHBOARD WAS TELLING EVERY USER THAT PLAYER B RAN 0.0 m, AND B HAD NEVER BEEN SEEN.** `distance_run_m` is a path INTEGRAL over per-frame player positions and was reported unconditionally. Measured on the committed perception caches, far-player coverage is **1.0%** (am_hard_utr), **11.0%** (yt_match40), **9.6%** (demo30) — and on a fresh yt_rally2 run it is **0.0%**, i.e. the shipped `analyzed_match.json`'s confident `"B": 0.0` was integrated over **zero observations**. The failure is DIRECTION, not noise: `_distance_run_m` forward-fills gaps, so a sparse track collapses into a *flat* path and returns a small precise-looking number instead of an obviously broken one — and the >2 m/0.25 s sanity cap then discards the real strides. `compute_stats` had already fixed this exact trap for speed (*"reporting 0.0 was indistinguishable from a broken pipeline"*); movement never got the same treatment. Now gated: below `pipeline.MIN_TRACK_COVERAGE` the value is **None (not measurable), which is NOT 0.0**, and the new `stats.player_track_coverage` ships the denominator alongside it (rule 5). **The bar is not invented** — it is the project's existing ≥50% seen-fraction bar for a trusted speed (Session M part 2), because it is the same question: is this track dense enough to integrate over. The working case is untouched (near-player coverage 74–92%; yt_rally2 A reads 61.4 m against the old 61.8 m). Frontend renders *"not tracked"* with the coverage percent instead of a zero-length bar, and an untracked player can no longer define the bar scale. `corrections.py` carries the coverage field with the distance so a correction replay cannot orphan an unexplained "not tracked". **SECOND GATE, on the axis coverage CANNOT see (added same day):** the density check above is blind to *identity*. `pose.select_players_on_court` keeps **one slot per court half** — deliberate and recorded in `tests/test_doubles.py`'s own docstring ("player tracking stays two-slot"), and `schema` has no C/D players to hold the partners — so in **doubles** that slot swaps between two people and the "path" teleports between them while **coverage stays high**. `_distance_run_m`'s 2 m/0.25 s cap then *discards* the swap steps for partners standing far apart and *adds* them for partners standing close, so the error has no fixed sign. Now refused outright when `infer_doubles` is true, with its own reason string in the new `stats.distance_run_note` (the UI must not say "too few frames" for a dense two-person track). **Verified end to end by forcing `--doubles` on yt_rally2: both slots refuse, and player A — 90.8% coverage, which would have reported a confident 61.4 m — is exactly the case the density gate could never have caught.** This is the review's P2-5 in its real form: NOT the singles net-exchange the review described (feet cannot legally cross the net mid-point, so the geometric split is sound there), but doubles. 9 tests, 400 total | 2026-08-17

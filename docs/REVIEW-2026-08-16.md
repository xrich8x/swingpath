# Review — 2026-08-16

Conducted per [docs/REVIEWER.md](REVIEWER.md). Read-only: no code was edited, refactored, or fixed while producing this. Every finding below was checked against the actual code (file:line), not against what the docs say the code does — four independent read-only passes verified the ball-detection, court/homography, dataset-hygiene, and engineering claims separately, plus a fifth, later pass (§3, "Computer Vision Technical Assessment") specifically judging whether the chosen CV techniques are the right ones, not just whether the code matches the docs.

---

## 1. Verdict

This is a single-camera tennis analyzer built almost entirely by an AI assistant from a non-engineer's specs, and it is unusually disciplined for that: a 2,159-frame human-labeled benchmark, working leak guards on both the ball and court training data, real homography reprojection checks, a coordinate round-trip test, a camera-movement watchdog wired into the actual pipeline (not just described), and a commit history that spends more space recording its own failed ideas than its wins. It currently proves that a fixed, well-mounted amateur camera can produce usable rally stats, shot placement, and approximate speeds — and, just as usefully, it has proven what it *cannot* yet do: reliable near-line calls below roughly a 3 m mount, or a validated point/game score on any clip, because that layer has no ground truth at all. The single most important thing to fix is not a bug but a methodology gap: the same 1,851-click gold set that is the project's only source of truth has also been the direct target of dozens of hyperparameter sweeps (detection threshold, gap policy, suppression radius, and more) over the past six weeks, so it is functioning as a validation set rather than a genuinely held-out test set — every headline recall and false-fire number in SCOREBOARD.md should be read with that caveat, and it is invisible from reading the docs alone. A close second: all 2,159 labels came from one person, once, with no second pass or agreement check, so the reliability of the ground truth itself has never been measured. Below the methodology layer, the code is close to what the docs claim — the exceptions are a two-week-stale maintenance doc that lists two already-fixed issues as open, and a "beats TrackNet/WASB" claim that rests on a comparison run before the current detector existed.

## 3. Findings

### P0 — invalidates results

**P0-1. The gold benchmark has been used to select hyperparameters, not just to report final numbers, so it is a validation set wearing a test set's reputation.**
`tools/tune_smoother.py:53,65-141` and `tools/tune_suppress.py:1-15,32-38` both evaluate candidate settings (`max_gap_s`, suppression segment thresholds, and — per SCOREBOARD's Session F — `score_thresh`, `acquire_bound_m`, resolution, and more) directly against `data/gold/*.labels.json`, the identical fixed set of 1,851 clicks that also produces every headline recall/false-fire number reported in SCOREBOARD.md. Over roughly six weeks the project has run more than a dozen such sweeps.

*Why it matters, in plain terms:* a "test set" is only meaningful if nothing about the system was chosen by looking at it. Once you've tried 15 different threshold values and kept the best-scoring one *against the same 1,851 clicks*, the reported number is biased upward relative to how the system will actually perform on a genuinely new clip — even though no model weight was ever trained on those clicks. This is the textbook failure mode ML_PRACTICES.md itself names ("never let a model grade its own homework") — just one level removed, at the hyperparameter layer instead of the weight layer.

*Mitigating factors, stated plainly so this isn't overstated:* the project's own "pre-register the gate before running the experiment" discipline (SCOREBOARD.md, Method rule 2) genuinely limits the worst version of this — cherry-picking after the fact — and the "What has not worked" table is *longer* than "What has worked," which is a real (if partial) signal against wholesale overfitting to the set. But pre-registering a gate for each individual sweep does not prevent the cumulative effect of many sweeps against one fixed set.

*What happens if ignored:* every future model or pipeline change will keep being graded against a benchmark that's already been partially fit to, and the gap between "what SCOREBOARD.md says" and "what a brand-new clip actually gets" will keep silently widening.

**P0-2. All 2,159 gold labels came from one person, one pass, with no consistency check.**
`tools/gold_label_server.py:10-11` states the tool is "deliberately blind" — but blind to the *model's* output, not duplicated across a second labeler or a second pass by the same one. A repo-wide search for "agreement," "kappa," "double-label," "second annotator" turns up nothing that measures label reliability; every "agreement" hit in the codebase means tracker-vs-human agreement, a different and already-critiqued concept (SCOREBOARD's own Trap T12: "a labeller who cannot find the ball clicks the most ball-like thing in the frame... agreement rises while truth does not").

*Why it matters:* the entire project's credibility rests on "score only against independent human labels." If that human's own clicks aren't internally consistent — click fatigue, a shifting mental definition of "unsure" over 2,159 labels collected across multiple sessions — there is currently no way to know, because it has never been measured.

*What happens if ignored:* a subtle, unmeasured amount of noise sits underneath every number in SCOREBOARD.md, and there's no way to distinguish "the model got worse" from "the labels drifted" if a future number looks surprising.

### P1 — blocks progress

**P1-1. No recent, dated re-run of the BallNet-vs-TrackNet-vs-WASB baseline comparison.**
The harness to do this exists and works — `tools/ball_perception.py:76-77` genuinely supports `--ball-model {tracknet,wasb,fusion,ours,all}`, and `eval_gold.py` can score any of them. But `tools/eval_detector_gold.py:258-259` — the more actively used tool — hardcodes `OurBallDetector`, and the only baseline evidence refreshed in the last month is against COCO's generic "sports ball" class (`data/output/racquet_negation_k.md`, 2026-08-13: COCO 35.4% recall@10px vs BallNet v21's 69.4%). The "beats TrackNet" framing traces to docs/archive/HANDOFF.md's 2026-07 numbers — from before hard-negative mining, the +57% data expansion, and three architecture-adjacent sessions. Without a fresh run, there's no current, honest answer to "is the custom model still worth its training cost over the open-source alternative."

**P1-2. The shipped eval uses τ=10px and never computes F1 or AP — not comparable to any published baseline, including the ones this review's own reference bar cites.**
`eval_gold.py:114` defaults `--radius=10.0`; grep across `eval_gold.py` and `eval_detector_gold.py` for precision/F1/AP returns zero matches — only hit/wrong/miss/false-positive rates. This may be a reasonable, deliberate choice (a far-court ball is only ~2-6px at the working resolution, so τ=4px could be unreasonably strict), but it is not stated anywhere as a deliberate deviation. Practically: if you or anyone else ever lines up "our BallNet gets X% hit@10" next to a paper's "WASB gets F1 95.6," that comparison is invalid on two axes at once (different metric, different threshold) even before accounting for amateur-vs-broadcast footage.

**P1-3. No human-assigned visibility/occlusion label — only a synthetic one used at training time.**
`train_ballnet.py:316,352`: `occluded=True` is set only when training-time augmentation *pastes* an occlusion patch onto a frame; it's never something a human labeler records. The actual label schema (`gold_label_server.py`) is exactly three categories: ball / no-ball / unsure. This means the project cannot break its own real-world eval down by "how occluded was the ball" the way ML_PRACTICES.md's own "stratify the benchmark" rule calls for — the existing stratification (serve/near/far/disagree/no-ball, from HANDOFF §11) covers court depth and disagreement, not occlusion, blur, or lighting.

**P1-4. The rally/score layer has zero ground truth of any kind, and this is not a small gap.**
SCOREBOARD.md's own Open table states it plainly: "Ball has 1851 human clicks, court has 20 clips, speed has the HUD and synth_truth; rallies and score have **nothing**." A prior attempt to derive score truth from a clip's burned-in scoreboard was built and then explicitly rejected by the user (self-consistency of a scoreboard isn't the same as correctness against the court — an instance of the same self-grading trap the project otherwise guards against well). No replacement has shipped. Rally segmentation is estimated (from the project's own count-from-pixels spot check) to over-split real matches by roughly 1.6×, and this is currently un-fixable with confidence because there's nothing to measure a fix against. For a PM: **the score and point count the dashboard shows should currently be treated as unvalidated**, distinctly from ball tracking or line calls, which do have honest numbers behind them.

**P1-5. `docs/NEXT_FIXES.md` is itself two weeks stale, including citing already-fixed issues as open.**
Both fixes it lists as outstanding (README's bad calibration example, the untracked eval-ladder files) landed in commits `a64f6e9` and `bf03f82` on 2026-08-02 — and the doc was last edited by commit `e63df5b`, *minutes after* both fixes, and never updated to reflect them. Its "209 tests pass" line is also far behind the current 391. This is a small, self-contained instance of the exact failure mode this whole review is designed to catch (a doc claiming something the code no longer does) — found inside the project's own maintenance tracker.

**P1-6. A real TrackNetV4-style motion-attention module is already built into BallNet, but it was dismissed by argument rather than by an actual training run.**
`_ballnet.py:29-51` (`MotionPrompt`) computes frame-difference maps (`|f0-f1|`, `|f1-f2|`) and uses them to gate the heatmap output — a genuine architectural feature, auto-detected from checkpoint keys at load time (`ball.py:1069-1072`) — but the shipped `ballnet_v21.pt` was trained without it. SCOREBOARD.md records the decision as "skipped on evidence" (confusers move with a person, so a staticness signal wouldn't separate them), but no training run with `motion_attention=True` was ever performed — that's an a priori argument, not a measurement, and it conflates two different signals: *whether* something moves (which the project correctly showed doesn't discriminate) and *what shape* of motion it is (a ball's smooth ballistic streak vs. a racquet's tight arc pinned near a wrist), which a learned module could in principle pick up but was never given the chance to. Full recommendation in the CV Technical Assessment below.

*Why it matters:* this is the one place in the project where its own "it should work is not a result — run it" rule (ML_PRACTICES.md) appears not to have been applied to a promising, cheap, already-built experiment.

### P2 — quality and maintainability

**P2-1. CourtNet training is unseeded, unlike BallNet training.** `train_courtnet.py` has zero matches for `seed`/`manual_seed`/`Generator(`, while `train_ballnet.py:478-508` fully seeds Python/NumPy/Torch/CUDA/DataLoader. Any future CourtNet A/B comparison would inherit the exact "arms differ by more than the flag under test" problem that SCOREBOARD's Trap T10 already diagnosed and fixed for BallNet.

**P2-2. Dependencies are unpinned.** `requirements.txt` and `requirements-ml.txt` use only `>=` bounds. Combined with the project's own documented finding that CPU vs GPU (and, by extension, library version) can flip near-threshold detections, an unpinned environment is a live, if partial, threat to reproducing any cited number a year from now. The provenance-stamp system (`pipeline.py:770-793`) mitigates this for *weights*, not for the surrounding library stack.

**P2-3. No written label schema outside the labeling tool's own UI copy.** `gold_label_server.py:240-241,277-283` embeds the one substantive labeling rule ("a ball in play is somewhere different on every frame") as HTML footer text. This is real, hard-won guidance (it fixed a measured false-labeling problem in Session J), but it lives nowhere a future labeler — or a future session picking this back up — would find it without opening the tool's source.

**P2-4. No experiment-tracking system, and the markdown-log substitute has no staleness detection.** No W&B/MLflow/TensorBoard anywhere in the repo. The markdown-log pattern (`data/output/*.md` + SCOREBOARD.md, enforced on every code commit by `.claude/hooks/scoreboard-guard.sh`) is a reasonable, low-overhead substitute at this project's scale — but as P1-5 shows, it has no equivalent enforcement for *secondary* docs like `docs/NEXT_FIXES.md`, which drifted for two weeks with nothing catching it.

**P2-5. Player identity is re-derived from scratch every frame — no persistent tracking across a clip.** `pose.py`'s near/far player split (`select_players_on_court`, `pose.py:289-333`) is a stateless per-frame geometric heuristic (whoever sits closest to the court centerline on each half); no IoU/Hungarian frame-to-frame ID assignment exists anywhere in the pose stack. This is likely fine for a standard rally where players stay on their own halves, but is a real, currently *unmeasured* risk at a net exchange or when a player is pulled deep into the opponent's half — exactly the case ML_PLAYBOOK.md names as necessary tennis-specific pose work ("stable IDs across crossings — don't swap players at the net"). No confirmed instance of a wrong output from this was found; it's a latent gap, not an observed defect.

### P3 — nice to have

**P3-1.** `run.py:343`'s `--ball-model` help text still says `ballnet.pt` where the actual shipped default is `ballnet_v21.pt`. Cosmetic.

**P3-2.** `test_gold_parity.py` and `test_goldset_registry.py` are named in a way that suggests they test the train/test leak guard; they actually test frame-alignment correctness and registry-count regression respectively — real, useful tests, just not the ones their names imply to a new reader.

### Computer Vision Technical Assessment

Everything above checks whether the code does what the docs claim. This section is different, per follow-up request: independent judgment, as a CV engineer, on whether the *techniques* actually chosen are the right ones — including where I disagree with the project's own reasoning, and concrete next experiments, roughly ordered by expected value per unit of effort. Verified by a fifth read-only pass, same rules as the rest of this review.

**1. Ball detector — the promising, cheap experiment is the motion-attention module, and it was never actually run (see Finding P1-6).**
`_ballnet.py:29-51`'s `MotionPrompt` is a real TrackNetV4-style component, already wired end to end, sitting unused in the shipped model. Given the architecture exists, the hard-negative infrastructure (Session I's localized confuser weighting) already exists, and a training run costs roughly the 1-2 hours of GPU time the project's own sessions routinely spend, I'd run this once with `motion_attention=True` before concluding it doesn't help. It's the single highest-value-per-hour item in this whole assessment because everything needed to test it already exists — it just needs to be turned on.

**2. Occlusion/visibility work is 2 of TOTNet's 3 components — the missing piece is the higher-effort one, so sequence it after #1, not before.**
The solid-patch occlusion augmentation and the visibility-conditioned per-sample loss weight are real and their measured gain (82.9→84.9) is genuine. What's missing is TOTNet's 3D temporal convolution — BallNet is still a plain 2D U-Net over channel-concatenated frames, so cross-frame reasoning is only ever learned implicitly through the concatenation, never architecturally encoded. This is a legitimate next step but a much bigger lift (new architecture, full retrain, re-verify nothing regressed on the gold set) than flipping a training flag, so I'd sequence it behind #1.

**3. RacketVision is blocked by a real dependency conflict, not "not yet tried" — and there's a cheaper path to test the same idea.**
`tools/eval_racquet_head.py` documents that RacketVision needs a legacy `mmcv==2.1.0`/`mmdet==3.3.0`/`mmpose==1.3.2` stack that doesn't coexist with the project's current torch install. Rather than standing up a second, legacy CV environment to borrow one external checkpoint, the cheaper in-house route is to reuse the training infrastructure BallNet and CourtNet already have — a small auxiliary racket-keypoint head, trained on a few hundred frames sampled from the *already-known* confuser locations (the mined hard negatives where a racquet fooled the ball detector) — to test the same underlying question (does knowing the racquet's head, not just its box, help) without the dependency risk. Worth doing only if racket negation stays a priority: SCOREBOARD.md's own numbers on the box-only version (54.5% catch at 4.5% collateral, 5.5 points under gate) say this is a real but modest lever, not a guaranteed win.

**4. CourtNet: I'm confirming the project's own call here, not adding a new one.**
ML6's recommendations (MAE loss, a MobileNetV3 backbone) were never applied to CourtNet — it uses weighted MSE and a custom VGG-style CNN — but the local-Hough per-keypoint refinement *was* applied. Given SCOREBOARD.md's own finding that CourtNet is "the wrong target" (classical courtfit consensus already wins on this footage, with zero wrong courts ever auto-accepted across 20 gold clips), I would not spend effort finishing this part of the SOTA-survey checklist. This is a case where the right CV recommendation is to leave it alone, even though the project's own literature research flagged it as a "steal" — the technique gap is real but the component isn't the bottleneck.

**5. Player tracking has no frame-to-frame identity (see Finding P2-5) — standard, well-understood fix, no research needed.**
A simple greedy or Hungarian assignment between this frame's player detections and the last frame's tracked boxes (by IoU or centroid distance) would close this. It doesn't need a research pass — just implementation and one test clip with a genuine net exchange to verify against, since none of the current gold clips are confirmed to have exercised this path.

**6. Spin/shot-type classification: the heuristic is the right call for now — I'd resist upgrading it.**
`classify_spin` (`events.py:592-628`) is a fixed-threshold wrist-displacement rule, not the learned pose-sequence model ML_PLAYBOOK.md describes as standard practice. Normally that reads as a technique gap worth closing — but this project has no spin ground truth to train or score a fancier model against (docs/archive/HANDOFF.md's own past spin comparisons were n≈3 and explicitly called weak evidence). Building a sequence model before the labels exist to justify it would be exactly the "data before model" mistake this project's own docs warn against elsewhere. Leave this alone until spin ground truth is collected specifically to support it.

**7. Bounce handling: both attempted fixes hit the same root cause (sparse detections near a bounce) — the next idea should target that cause, not add a third reset-threshold variant.**
The shipped mechanism is `reset_after=3` consecutive rejected detections (`ball.py:634`) — a fixed counter with no model of *why* the discontinuity happened. A more physically-grounded alternative (detecting the actual velocity-sign-flip of a bounce) was built and tested, and it failed its own pre-registered gate for what looks like the same underlying reason the simple counter underperforms: near a bounce on the harder clips, real detections are too sparse for either a fixed-N counter or a single hard reset to have enough evidence to act on confidently. I would not recommend a third "count until N, then reset" variant. This is a good candidate for an **Interacting Multiple Model (IMM) filter** instead — two parallel motion models (a "flight" constant-acceleration model and a "bounce" model with a discontinuous velocity prior), blended every frame by Bayesian model-probability mixing rather than waiting for N consecutive rejections. IMM filters are the standard tool in target-tracking literature for exactly this kind of maneuvering-target problem (a bounce is a maneuver event), and they update belief every frame instead of needing consecutive confirmations — which should help precisely where detections are sparse. This is a bigger implementation lift than a threshold tweak, so I'd only take it on if the ~48% of shots with untrusted speed (tied to losing the ball after landing, per SCOREBOARD's Session M) is still a priority after the rally/score ground-truth work in Finding P1-4.

## 5. Reality check on targets

Nothing in this repo's documentation claims Hawk-Eye-level or even ideal-SwingVision-level accuracy — that overreach, which the reference bar above is specifically designed to catch, simply isn't present. If anything, this project already does the reference-bar's job on itself: CLAUDE.md's Gotchas section states outright that a 1.0 m camera mount is "worse than guessing" on close calls, and that number is real (`calibration.expected_call_accuracy`, verified in Finding row 19).

**Achievable with the current capture setup** (a fixed phone/camera on a fence or tripod, 720p-1080p, often 1.4-1.8 m off the ground): rally statistics, shot counting, coarse shot placement, and approximate average ball speed (already correctly framed as 15-20% under a radar's peak reading, and the code doesn't try to correct that away). This matches this review's own stated realistic ceiling for a single amateur camera almost exactly.

**Needs a capture change, not more ML work:** authoritative near-line calls. At the project's own measured amateur mount heights (1.38 m and 1.74 m), close-call accuracy sits at roughly 58-60% — barely above the 56.2% floor of just always answering "in." The project's own height-curve measurement shows this climbs to ~69% at 3 m and ~80% at 6-8 m. If reliable line calls matter to you, the lever is a taller or farther-back mount (and, secondarily, recording at 60fps and using `--full-rate`), not a better detector — the code and the docs already agree on this and surface it to the user via `run.py check`.

**Not achievable at all with one camera, regardless of mount:** Hawk-Eye-grade (millimeter) accuracy — that system uses 10+ synchronized cameras at ~340fps and isn't a fair comparison to anything here, and nothing in this repo claims otherwise.

**One live discrepancy worth flagging here specifically:** the project's own ball-recall numbers (roughly 70-80% hit@10px on amateur footage, per SCOREBOARD.md) are not directly comparable to the WASB/TrackNetV3 broadcast numbers in this review's reference bar (F1 95.6-98.6) — different metric (hit-rate vs F1), different threshold (10px vs the field's 4px), and different footage difficulty (amateur single low camera vs stable elevated broadcast). Directionally it's consistent with "amateur footage is harder," which is honest, but a true side-by-side needs Finding P1-1's re-run using a shared metric.
